# Execution-State and Error Models

## Authority and Scope

DEV-480 consumes Draft `0.1.0` at public revision `59d49364d85e48cc8e69c762d130a7a86dc1fe65`: [Measurement Result](https://github.com/tv-rain/barometer-spec/blob/59d49364d85e48cc8e69c762d130a7a86dc1fe65/data-formats/measurement-result.md#REQ-RESULT-0019), [Task Trust](https://github.com/tv-rain/barometer-spec/blob/59d49364d85e48cc8e69c762d130a7a86dc1fe65/library/task-trust.md#REQ-TRUST-0033) and [Task Schedule](https://github.com/tv-rain/barometer-spec/blob/59d49364d85e48cc8e69c762d130a7a86dc1fe65/data-formats/task-schedule.md#REQ-SCHEDULE-0022). Public text controls behavior; this document records the narrower Go implementation.

`internal/model/task` owns the eleven admission-error codes (the ten initial REQ-TRUST-0034 classes and `task_unsupported`, added by DEV-597 for REQ-TRUST-0036) and all fifteen execution reasons. `internal/execution` owns a pure attempt value and, since DEV-635, the [run orchestration](#run-orchestration) engine that drives it. Both use only existing dependencies and introduce no public facade, third-party dependency or new serialized schema. `task.ErrorContract` and `execution.Contract` identify the `0.1.0` vocabularies. Internal enum ordinals are not wire identifiers. Admission errors and attempts reject JSON import and export, including import into an existing value; future result and operational interfaces must use their reviewed contracts.

## Admission Errors

`NewAdmissionError` accepts a closed numeric `AdmissionCode`; zero and unknown codes are rejected. The error stores only that code and formats it as the public operational class. It has no payload, target, platform message, wrapped cause or arbitrary text field. Admission errors are distinct from `ExecutionReason` and cannot be passed to `Attempt.Stop`. A zero error value formats to a fixed invalid-error message and carries no valid code.

Existing decoding/configuration/validation sentinels retain their current contracts. The future admission owner must deliberately map failures at the appropriate stage. This task does not authenticate, authorize, reject deliveries, persist replay state or generate Measurement Results for invalid tasks.

## Attempt Transitions

An attempt is a copied value with private state; callers must retain each returned successor. Failed operations return the unchanged value and a fixed error. Zero is invalid. `NewAttempt` starts pending; it does not prove admission or eligibility.

| Current phase | Start | Complete | Stop with registered reason |
|---|---|---|---|
| Pending | Running | Reject | NotRun |
| Running | Reject | Completed | Incomplete |
| Completed, Incomplete, NotRun, or zero | Reject | Reject | Reject |

Pending and Running are internal phases. Completed, Incomplete and NotRun correspond to the public terminal states. Complete accepts no reason or protocol error; negative DNS, TCP, TLS and HTTP observations can still be terminal measurement outcomes. Stop accepts only a valid `ExecutionReason`, with unknown values, protocol failures and admission classes rejected even after an explicit string conversion. Terminal states cannot be reopened and subsequent conditions cannot replace the first reason.

The future runtime owner must serialize competing events and establish whether execution started, whether a runner produced a terminal outcome, and which outer condition occurred first. This value provides neither synchronization nor cancellation/cleanup, clocks, counters, path snapshots, policy enforcement or resource accounting. It must not be shared as mutable runtime state without an owning synchronization mechanism.

The future result constructor must require measurement data for completed results, forbid it for not-run results, and permit bounded incomplete output only where the test schema allows it (initially NET-05). This attempt model carries no protocol data or partial-result payload and cannot validate those result-envelope obligations.

## Retry Boundary

`RetryReason` returns a candidate only for a terminal incomplete/not-run attempt with `platform_suspended`, `network_context_unavailable`, `proxy_unavailable` or `internal_error`. It reuses `task.Retryable`, preserving existing task decoding and schedule semantics. Completed protocol outcomes cannot produce a retry candidate. Host cancellation, deadline/resource limits, policy rejection, network changes and other path failures remain non-retryable.

The candidate is not permission to execute. `validation.RetryEligible` must still enforce the accepted retry allowlist, attempt count, expiry, time window, realized due time, supported behavior and execution/safety constraints. Retry candidates create no new runs and do not bypass local policy or authorize network work.

## Run Orchestration

DEV-635 adds `execution.Engine`, the internal engine for one run of an admitted task. It is not exported through the root package; `Client.StartRun` (DEV-636, [Run Reservation](#run-reservation)) launches it, and `Client.CancelRun` (DEV-561, [Deadlines, Cancellation and Cleanup](#deadlines-cancellation-and-cleanup)) stops it. Public baseline: Draft `0.1.0` at [`4743b63`](https://github.com/tv-rain/barometer-spec/tree/4743b636f29feb1f0f8d042866d04ccda3532938) for [Retry](https://github.com/tv-rain/barometer-spec/blob/4743b636f29feb1f0f8d042866d04ccda3532938/data-formats/task-schedule.md#retry) and [Schedule and Retry Limits](https://github.com/tv-rain/barometer-spec/blob/4743b636f29feb1f0f8d042866d04ccda3532938/library/registered-limits.md#schedule-and-retry-limits).

`NewEngine` takes the registry, a `Clock` (monotonic `Now`, a cancellable `Wait` and an `AfterFunc` timer), a `Jitter` source and the `Output` port; any missing input fails with `ErrEngine`. `SystemClock` and `LocalJitter` (uniform, from `crypto/rand`; a read failure yields no jitter) are the non-test implementations. A `Plan` carries only trusted local inputs prepared after admission: task ID, exact test version, normalized parameters, the validated schedule, the attempt deadline (the effective `max_duration_ms`, at most `MaxAttemptDuration` = 60 s, or `ErrPlan`), the effective attempt limits after admission (DEV-562, [Attempt Byte and Connection Budgets](#attempt-byte-and-connection-budgets)), the host-directed eligibility snapshot (`validation.StartContext`, whose `Now` the engine sets), the task's network conditions (DEV-644), the implementation identity, a `result.Decoder` bound to the same task, a `ContextSource` and a `DialerSource`.

`Run` fails closed before any work, with no result, no context capture, no dialer and no runner call, on an invalid plan (`ErrPlan`) or a missing runner (`ErrNoRunner`). It then draws one run ID (`result.NewRunID`) shared by every attempt of the run. A run whose context has already ended records attempt 1 as `not_run` with the cancellation reason and does nothing else. Otherwise a run that `validation.RunEligible` rejects fails closed (`ErrNotEligible`) with no result, and attempts execute in order, each under its own deadline ([Deadlines, Cancellation and Cleanup](#deadlines-cancellation-and-cleanup)):

1. Capture the access snapshot and evaluate the task's network conditions against it ([Network Conditions and Access Context](#network-conditions-and-access-context)). An ended attempt context is `not_run` with the cancellation reason. An unsatisfied or undeterminable condition is `not_run` with `constraints_unsatisfied` before the first attempt; before a retry it ends the run with no second attempt and no result. Without a network condition, a failed capture is `not_run` with `internal_error`; `network_context_unavailable` is kept for required Network Context fields (REQ-EXECUTION-0031). From the capture on, an access-network generation change cancels the attempt with `network_changed`.
2. Obtain a fresh dialer for the attempt number. A failure is `not_run` with `internal_error`.
3. Invoke the registered runner once through the attempt scope. A terminal output becomes `completed` with its measurement and Network Context. A runner error becomes `internal_error`, or the cancellation reason when the attempt context ended, and is `not_run` or `incomplete` depending on whether the test started. An attempt whose budget the scope exhausted is `incomplete` with `resource_limit`, even when the runner still returns an outcome. Output that result construction rejects for the test is not retained: the attempt becomes `incomplete` with `internal_error`.
4. Build the result through `result.Decoder.Build` and write it to the `Output` port. A `not_run` result never carries Network Context. Writes use a context that the run's cancellation does not end, so a cancelled attempt is still recorded and a racing cancellation cannot discard a committed outcome; the output port bounds its own writes. Any write error, including an uncertain commit, ends the run with `ErrOutput`; the write is not repeated and no further attempt starts.
5. Decide a retry. Only an attempt whose reason is a registered retry candidate (`Attempt.RetryReason`) can retry, and only when `validation.RetryEligible` accepts it before the wait. With at most two attempts, `fixed` and `exponential` backoff both produce `initial_delay_ms`; the engine adds local jitter in `[0, jitter_ms]` and caps the realized delay at `max_delay_ms` (REQ-SCHEDULE-0029). It does not retry when the realized delay would reach `not_after`, waits on the injected clock, and checks `validation.RetryEligible` again afterwards, so a closed time window or expired task ends the run. Completed attempts, including negative protocol outcomes, never retry (REQ-SCHEDULE-0025).

A run context that ends after an attempt prevents every further attempt, including a permitted retry and one already waiting in its backoff. The `Report` lists each terminal attempt written to the port, with its attempt value and, since DEV-562, the scope's metered `Usage` rather than the runner's report; it stays valid when `Run` returns an error.

These are reviewed implementation inputs, not new public limits:

| Retry delay | `initial_delay_ms` plus jitter up to `jitter_ms`, capped at `max_delay_ms`, never reaching `not_after` | REQ-SCHEDULE-0028, REQ-SCHEDULE-0029 |

### State Mapping and GO-SPEC-ISSUE-004

Since DEV-561 the engine follows the [GO-SPEC-ISSUE-004 disposition](specification-issues.md#go-spec-issue-004-boundary-between-not_run-and-incomplete) at public [`84f52f8`](https://github.com/tv-rain/barometer-spec/tree/84f52f8872a5af9e6d97894611e3b2eaba18aba8):

- **Test start (REQ-RESULT-0051).** An attempt is `not_run` until the test starts and `incomplete` after, when an outer condition stops it. The test starts at its first dial through the attempt scope or, for a runner that observes network state before dialing, when it calls `measurement.Input.Start`. Context capture, dialer acquisition and the runner's local validation do not start it. A runner that returns a terminal outcome has started.
- **Recorded outcome (REQ-RESULT-0052).** A returned outcome is `completed`, even when a cancellation or the deadline arrives while connections close. A runner interrupted before its outcome returns `measurement.ErrRunner`.
- **Network Context (REQ-RESULT-0053).** No `not_run` result carries Network Context, and `result.Decoder` rejects one that does; the former captured-context binding is removed.
- **Reasons.** An expired attempt deadline is `attempt_deadline_exceeded`. `CancelRun` and lifecycle transitions are host requests and record `cancelled_by_host`. The first cancellation is kept: a deadline that expired before a host cancellation stays the reason, and the reverse. An exhausted attempt byte or connection budget is `resource_limit` (DEV-562). An access-network generation change is `network_changed` (DEV-644). A proxy endpoint or CONNECT failure is `proxy_unavailable` or `proxy_connect_failed`, and a failed pre-attempt path check `proxy_not_configured`, `proxy_not_permitted` or `proxy_path_unsupported` ([Proxy Path](#proxy-path)). A host proxy replacement or clearing cancels the affected proxy generation with `proxy_reconfigured`; direct runs continue. `platform_suspended` remains DEV-455.

NET-05 composite states (REQ-NET-05-0061) and the unsatisfied-network-condition rule (REQ-EXECUTION-0031) need no engine change: no NET-05 runner exists (DEV-454), and network conditions are unsatisfied at the start gates, which produce no result.

## Deadlines, Cancellation and Cleanup

DEV-561 adds deadline and cancellation coordination. The public bounds are the attempt deadline, the wall-clock limit of the complete attempt including context acquisition and cleanup ([REQ-LIMIT-0006](https://github.com/tv-rain/barometer-spec/blob/84f52f8872a5af9e6d97894611e3b2eaba18aba8/library/registered-limits.md#REQ-LIMIT-0006)), and cleanup that stops within 2,000 ms of it ([REQ-LIMIT-0008](https://github.com/tv-rain/barometer-spec/blob/84f52f8872a5af9e6d97894611e3b2eaba18aba8/library/registered-limits.md#REQ-LIMIT-0008)).

- **Attempt deadline.** Each attempt runs under a child of the run context. An `AfterFunc` timer on the engine clock, armed when the attempt begins and stopped when it ends, cancels it with a deadline cause after `max_duration_ms`. Tests drive it with `testkit.WaitClock`, whose timers fire only when the test advances the clock.
- **Attempt scope.** The runner receives the scope in place of the path's dialer. It records the test start, ties every dial to the attempt context, and owns every connection opened through it: when the attempt context ends it closes them, which interrupts blocked reads and writes, and it refuses later dials. When the runner returns, the scope closes whatever the runner left open. Operating-system buffering and retransmission below the dialer are outside this guarantee and outside the counted budgets ([REQ-LIMIT-0033](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/registered-limits.md#REQ-LIMIT-0033)).
- **Run cancellation.** `StartRun` gives each run its own context, a child of the generation context. `CancelRun` cancels it and waits for the run's engine to return, for at most `CleanupBound` on the engine clock; lifecycle transitions cancel the generation context and wait for runs through their reservations, for at most the lifecycle deadline. A run ends with no further attempt.
- **Cleanup failure.** The engine cannot stop a runner that ignores its context, so it never reports cleanup as done before the runner returns. The run stays active, keeps its reservation (active-run count, exclusive flag and pending-output allowance) and starts no attempt, while its connections are already closed and new dials refused. `CancelRun` returns `cleanup_incomplete` and a later call waits again; `Close`, clearing and policy replacement return `cleanup_incomplete` or `clearing_incomplete` and stay blocked and retryable. Failure to clean up is a local condition, not a result field.

There is no separate run deadline: the public text defines none. A run is bounded by at most two attempts, each with its deadline, and a retry delay that never reaches `not_after`.

## Attempt Byte and Connection Budgets

DEV-562 meters the attempt scope, adopting the [GO-SPEC-ISSUE-005 disposition](specification-issues.md#go-spec-issue-005-which-bytes-count-toward-attempt-byte-limits) for the generic stream layer at public [`5d01879`](https://github.com/tv-rain/barometer-spec/tree/5d01879cfd1d47396c780befa2567f7e90439948). Attempt byte limits count where the attempt exchanges test bytes with a transport ([REQ-LIMIT-0034](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/registered-limits.md#REQ-LIMIT-0034)); for every runner that boundary is the `measurement.Conn` the scope returns, so the scope counts there and a runner's own read caps and `Usage` report decide nothing.

- **Effective limits.** `Plan.Limits` carries the attempt limits that admission narrowed to the task's values within the intersected issuer and local ceilings, so they are already the stricter of the task, local and registered values. The engine rejects a plan whose byte or connection limit is negative or above its registered maximum with `ErrPlan`, and never clamps. Zero permits no traffic ([REQ-LIMIT-0007](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/registered-limits.md#REQ-LIMIT-0007)).
- **Connections.** Every dial through the scope counts toward `max_connections` before it reaches the path's dialer, whether or not it connects; a refused connect has already sent traffic. A dial beyond the limit is not issued.
- **Sent bytes.** A write is issued only when the remaining sent budget covers all of it, so a write that would exceed `max_bytes_sent` sends nothing. A partial write counts only the bytes the stream accepted.
- **Received bytes.** Each read requests no more than the remaining received budget, so bytes a runner reads ahead into a buffer count when they are read and the counter never exceeds `max_bytes_received`. A read with no budget left is refused, so a runner that reads exactly the limit completes and one that needs one more byte is stopped.
- **Stop.** An operation the remaining budget cannot cover returns an error to the runner and cancels the attempt context with a budget cause. The scope then closes every connection and refuses further dials, reads and writes, as for the deadline and host cancellation, and the attempt is `incomplete` with `resource_limit` ([REQ-LIMIT-0027](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/registered-limits.md#REQ-LIMIT-0027), [REQ-LIMIT-0028](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/registered-limits.md#REQ-LIMIT-0028)). The stop is the first termination, so an outcome the runner returns afterwards is not recorded as `completed`. The first cancellation cause is kept, as for the deadline and host cancellation. `resource_limit` is not a retry candidate, and every attempt gets a fresh scope and budget.
- **No fallback.** Budget handling never requests another dialer or path; a refused operation ends the attempt.

Not counted at this layer, as the public text requires: TLS handshake and records, TCP/IP and UDP/IP headers, operating-system retransmissions and buffering, proxy transport framing and the `CONNECT` exchange with the loopback proxy endpoint, which belong below the stream a runner receives, and Network Context acquisition, whose lookup dialer is not wrapped in the scope ([Egress Network Context](#egress-network-context)). Whether a runner's HTTP headers, DNS messages, DoH framing and DoT length prefixes cross this boundary as counted test bytes, how a TLS runner's plaintext is metered, UDP datagram accounting and the NET-05 aggregate limits are per-protocol evidence for the runners and codecs under DEV-454, which must route their traffic through this scope. The proxy dialer places the `CONNECT` exchange below the scope ([Proxy Path](#proxy-path)).

Since DEV-636 the engine also evaluates the plan's optional `Preconditions` before every attempt: unsatisfied before the first attempt, `Run` fails closed with `ErrNotEligible` and no result; unsatisfied before a retry, the run ends with the first attempt's result unchanged and no second attempt. The `Output` port gains `Capacity`, which run reservation checks before a run starts.

Since DEV-563 each initialized generation binds the engine to its own `pending.Store` ([Pending Results and Bundles](package-architecture.md#persistence-ports)), which also serves `Client.NextBundle` and `Client.AcknowledgeBundle`. The engine writes through a context without cancellation; the store bounds every call by the lifecycle deadline, so a stalled backend fails the write with an uncertain outcome instead of holding the run. `Capacity` counts results of the registered maximum size (65,536 bytes) that fit in new bundles within the remaining bundle and aggregate-byte limits, ignoring free room in the open bundle, so a bundle returned between the check and the write never reduces the room a reserved run counted on.

## Run Reservation

DEV-636 adds the start-time decisions behind `Client.StartRun` ([Implemented Subset](public-api.md#implemented-subset)). The host directs every wakeup; nothing here starts a run on its own.

### Run Accounting

`persistence.RunRecord` is the schedule accounting of one admitted task, keyed by its replay key and held in the `persistence.RunLedger` port: the anchor of occurrence 0, the number of reserved runs, the next occurrence that has neither been reserved nor skipped, and that occurrence's due time with jitter included. The record is written before a run exists, so an interrupted or uncertain write can only lose a run. Reinitialization does not reset it; its deletion by clearing belongs to DEV-564.

Retention (DEV-641, Go-local rule): a run record is retained no longer than the replay record of the same key. `RunLedger` methods receive trusted time; the production ledger, `persistence.State.Runs` ([Persistence Ports](package-architecture.md#persistence-ports)), stores the replay record's `RetainUntil` with each run record, refuses a write for a key without a retained replay record, purges run records before their replay records and, at initialization, deletes a run record whose replay record is gone. Because a replay record is retained past its task's `not_after`, the purge never removes the accounting of a task that can still run. Run reservation passes its run-clock reading; the test-only `internal/testkit/ledger` ignores it.

`execution.NewAccounting`, `Occurrence`, `Advance`, `Due` and `Reserve` implement the interim rule of [GO-SPEC-ISSUE-011](specification-issues.md#go-spec-issue-011-due-times-and-catch-up-for-interval-repetition): the anchor is `starts_at` (rounded up to a whole second) or the acceptance time; occurrence 0 is due at the anchor without jitter; occurrence *k* of an `interval` schedule is due at anchor + *k* × `interval` plus jitter drawn from the engine's `Jitter` source once, capped at the task's `jitter`; the current occurrence is the latest whose unjittered time has passed, and once that reaches `max_runs` the schedule has ended; earlier unreserved occurrences are skipped and consume no run. Repeat mode `none` permits one run. `validation.RunEligible` still decides `starts_at`, `not_after`, the time window and `max_runs` for the due occurrence.

When no run was reserved before a reinitialization, the anchor of a task without `starts_at` is the redelivery's acceptance time, which can only move occurrences later. This and every other part of the rule are interim until public disposition.

### Attempt-Start Gates

`execution.Gates` is the plan's `Preconditions`, evaluated by `StartRun` before reservation and by the engine before each attempt. Every missing capability, error or undetermined value is unsatisfied; nothing is guessed:

- **Network conditions.** Network Context requirements are not part of `Gates`: they depend on the attempt's own egress context, which the engine acquires and evaluates in each attempt ([Egress Network Context](#egress-network-context)). Either network path passes: a proxy task whose path cannot be used is started and its attempt records why ([Proxy Path](#proxy-path)). Since DEV-644, `allowed_transports`, `vpn_policy` and `require_validated` are not part of `Gates`: `StartRun` evaluates them with `execution.NetworkConditions` against the access values the path reads at reservation, and the engine evaluates them again against each attempt's own snapshot ([Network Conditions and Access Context](#network-conditions-and-access-context)).
- **Device.** `minimum_battery_percent` needs a known battery level at or above it, and `allow_charging_only` a known charging state, from `platform.Device`.
- **Consent.** Only for a task whose consent requirement admission recorded, `platform.Consent` must report `ConsentValid` ([Consent Handoff](admission.md#consent-handoff)). The query carries no task value. Absent, ended, unavailable, an error or a missing capability start no attempt and produce no result.

`StartRun` maps an unsatisfied gate, an unreadable access context and an unsatisfied network condition to `run_not_due`, so no result is written for it. A proxy path that cannot be used is not among them. Concurrency is the facade's, because it spans runs: an `exclusive` run starts only when no other run is active, and no run starts beside an active exclusive run. An absent concurrency member states no requirement and is treated as `shared`.

## Network Conditions and Access Context

Tasks with transport, VPN and validation conditions run on either network path when the platform reports the required values. Public baseline: Draft `0.1.0` at [`5d01879`](https://github.com/tv-rain/barometer-spec/tree/5d01879cfd1d47396c780befa2567f7e90439948) for [Network](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/data-formats/task-execution.md#network), [Access Context](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/network-context.md#access-context) and the [Access Object](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/data-formats/network-context.md#access-object).

- **Platform port.** `platform.Network` is defined from its consumer. `Access` returns one `platform.AccessState`: the network type, VPN state, IPv4 and IPv6 availability, validation state and an access-network generation. Each enumeration's zero value is unknown. The struct has no field for an interface name, address, DNS server, Wi-Fi or cell identifier, SIM, subscriber, carrier or location (REQ-CONTEXT-0003), so none can reach the core through it. `Watch` reports, once, that the generation moved past a given one. The query carries no task value. The native capability, its change signal and its binding are a review point of DEV-455; the test-only `capability.Network` fake scripts values, failures and generation changes.
- **Normalization.** `networkcontext.Normalize` maps a reading to the registered access vocabulary. A value outside the platform enumerations is `unknown`, never guessed (REQ-CONTEXT-0034). `network_changed` is false in a reading; only an attempt can observe a change.
- **Capture.** `networkcontext.Source.Capture` reads the capability once and binds the reading to the source's path in its generation: the direct path, or the proxy path of one proxy snapshot ([Proxy Path](#proxy-path)). It sends no traffic. A capability error, a zero generation or an ended context is unavailable. The snapshot provides the access values, the Network Context to attach (egress `{status: unavailable, lookup_source: none, network_path: direct}`, or `network_path: proxy` with the configured `connection_code`, until the attempt acquires egress, with `network_changed` false or true) and the watch. The source retains nothing between captures; egress classifications are cached only in the client's egress cache.
- **Evaluation.** `execution.NetworkConditions` applies REQ-EXECUTION-0016 to REQ-EXECUTION-0020 to one access reading. `allowed_transports` needs a reported `wifi` or `cellular` type in the list; `exclude` needs `not_detected` and `require` needs `detected`, so `unknown` never matches either; `require_validated` needs the platform's own `validated: yes`. An unset or unregistered `vpn_policy` is unsatisfied. No library connectivity check is made (see [GO-SPEC-ISSUE-013](specification-issues.md#go-spec-issue-013-library-internal-check-for-require_validated)).
- **At reservation.** The production `networkPaths` reads the access context once in `StartRun`, after the gates, concurrency and capacity checks and before the ledger write. An unreadable context, or a condition the reading does not satisfy, returns `run_not_due`, reserves nothing and writes no result. The run's result decoder is bound to the reservation snapshot's path; generation numbers are local metadata and never serialized.
- **At each attempt.** The engine captures a new snapshot inside the attempt deadline and evaluates the conditions again. Before the first attempt, an unsatisfied or undeterminable condition, including a failed capture, records `not_run` with `constraints_unsatisfied` and no Network Context, because the run was already reserved and counted. Before a retry it ends the run with no second attempt and no result, as an unsatisfied precondition does. This rule was approved for DEV-644.
- **Path snapshot.** Each direct attempt gets its own dialer from `execution.DirectDialers`, a zero `net.Dialer` that consults no proxy setting and keeps no connection pool. The attempt scope meters and closes every connection, as for any other dialer.
- **Network change.** The engine registers the snapshot's watch after the capture and stops it when the attempt ends. A change cancels the attempt with `network_changed`: before the test starts the attempt is `not_run` without Network Context; after it starts it is `incomplete`, and its Network Context records `network_changed: true`. A change after the outcome was recorded leaves the attempt `completed` with `network_changed: false` (REQ-RESULT-0052). A snapshot that cannot be watched reports a change at once, so no attempt runs unwatched.

The root package now links package `net` through `internal/execution`, and since DEV-647 also `crypto/tls` and `net/http` for the context endpoint request. `TestAdmissionHasNoNetworkDependency` keeps the closure of `internal/admission` free of network and TLS packages and requires `internal/execution` to be the only module package in the root closure that imports one; the import rule "only the network path dialers open sockets" keeps the root package and admission from importing network packages themselves.

Limits: no native network capability, change signal or Android and Apple adapter exists (DEV-455), so platform values, their coarseness and change detection are exercised only with the fake. The direct dialer is exercised only against `127.0.0.1`. Proxy lifecycle changes and egress acquisition are described below. Result decoders still take only the test identity as their Output contract; deriving the full Output plan from the registered test is DEV-454. Context observations are not evidence of censorship.

## Proxy Path

A task with `network_path: proxy` runs through the single local HTTP/1.1 CONNECT proxy the host configured at `Initialize` or `SetProxy` and never through the direct path. Public baseline: Draft `0.1.0` at [`5d01879`](https://github.com/tv-rain/barometer-spec/tree/5d01879cfd1d47396c780befa2567f7e90439948) for [Proxy Integration](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/proxy.md) and [Network Path](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/data-formats/task-execution.md#network-path).

- **Snapshot.** The proxy comes from `Initialize` or `SetProxy`. Its independent, in-memory generation changes on set or clear and is never persisted or serialized. A proxy run leases its snapshot before path planning, retaining it through the engine return and result write. A set or clear seals the old generation against new reservations, cancels its context with `proxy_reconfigured` and waits for every old lease before activation. The engine records the cancellation before start as `not_run`, or after start as `incomplete`, and starts no retry on the replacement or direct path. `ClearProxy` removes the configuration; the next separately scheduled proxy run records `proxy_not_configured`. Direct runs retain their contexts. Incomplete cleanup keeps the client blocked; lifecycle and policy changes cannot overlap a proxy transition. The NET-05 runner must use the same leased dialer for every step (DEV-454). A set or clear also drops the egress cache's proxy entries ([Egress Network Context](#egress-network-context)). At reservation `networkPaths` builds a proxy context source and `execution.ProxyDialers` for the snapshot's endpoint and binds the result decoder to the proxy path; network conditions are evaluated as on the direct path. Each attempt gets a fresh dialer of the same snapshot (REQ-EXECUTION-0009). Direct tasks are unaffected by the proxy configuration (REQ-PROXY-0012).
- **Pre-attempt check.** Before each attempt, ahead of the context capture, the engine applies the plan's `PathCheck` ([REQ-EXECUTION-0008](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/data-formats/task-execution.md#REQ-EXECUTION-0008)): a proxy is configured, the admitted path authority, which issuer and local policy bound, permits the proxy, and the registered proxy rule accepts the task's concrete parameters. The first failing condition records `not_run` with `proxy_not_configured`, `proxy_not_permitted` or `proxy_path_unsupported` and makes no contact; none is a retry candidate. A proxy task without a configured proxy is therefore started and counted rather than refused with `run_not_due`, so its explicit state is recorded ([REQ-EXECUTION-0010](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/data-formats/task-execution.md#REQ-EXECUTION-0010)); this rule was approved for DEV-645. Admission rejects a task that policy or the rule does not permit ([REQ-PROXY-0042](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/proxy.md#REQ-PROXY-0042)), and a policy replacement admits every task again, so in this build the last two conditions hold for every admitted task; the check re-applies them, and only engine tests with a scripted check produce those two states.
- **CONNECT.** Each dial through the attempt's dialer opens one connection to the loopback endpoint, refusing an endpoint that `localhost` resolves off loopback, and sends `CONNECT <authority> HTTP/1.1` with a matching `Host` field and nothing else, so no credentials, cookies or other application fields reach the proxy. The authority is an explicit IP address and port (IPv6 in brackets, no zone). A hostname is refused before connecting to the proxy endpoint or sending CONNECT ([REQ-PROXY-0043](https://github.com/tv-rain/barometer-spec/blob/bb805f07a36630db7250d5ab63006ed5e351f7a7/library/proxy.md#REQ-PROXY-0043)); no local DNS lookup or direct fallback makes it eligible. Only an `HTTP/1.1 2xx` status line with well-formed, CRLF-terminated header fields within the 8,192-byte head bound establishes the tunnel; framing fields of the 2xx response are ignored, and bytes the endpoint sends after the head are the tunnel's first bytes. The exchange ends with the attempt. Only `tcp` dials are carried: any other dial is refused before contact and ends the attempt with `internal_error`, because admission admits only compatible tasks. Tunnels are never pooled or reused, so a followed redirect opens a new tunnel on the same snapshot ([REQ-PROXY-0018](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/proxy.md#REQ-PROXY-0018), [REQ-PROXY-0020](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/proxy.md#REQ-PROXY-0020)).
- **Budgets.** The attempt scope wraps the proxy dialer: it counts each tunnel toward `max_connections` before it is opened and meters only the bytes exchanged inside the established tunnel, so the CONNECT exchange is not counted ([REQ-LIMIT-0033](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/registered-limits.md#REQ-LIMIT-0033)). Tests compare the metered counts with the bytes the scripted proxy relayed.
- **Failures.** A failed connection to the endpoint is `proxy_unavailable`; a non-2xx, closed, malformed or oversized response is `proxy_connect_failed`. The dial started the test, so the attempt is `incomplete` and keeps its proxy Network Context. The failure becomes the attempt's cancellation cause, so an outcome the runner builds from the failed dial is not retained: path states are execution observations, never the test's and never evidence of censorship ([REQ-PROXY-0029](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/proxy.md#REQ-PROXY-0029)). A CONNECT the attempt deadline cuts short is `proxy_connect_failed`; a host cancellation or a network change during the exchange keeps its own reason. `proxy_unavailable` is a retry candidate when `retry_on` lists it, and the retry uses a new dialer of the same snapshot. Nothing is ever retried through the direct path ([REQ-PROXY-0030](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/proxy.md#REQ-PROXY-0030)).
- **Result metadata.** Proxied results record egress with `network_path: proxy` and the configured `connection_code`, acquired through the same proxy generation, or `{status: unavailable, lookup_source: none}` when no egress classification is configured or available. No result carries the proxy host, port or generation, the CONNECT request or the proxy's response ([REQ-PROXY-0031](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/proxy.md#REQ-PROXY-0031) to [REQ-PROXY-0033](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/proxy.md#REQ-PROXY-0033)).

Limits: the CONNECT dialer is exercised only against the scripted proxy of `internal/testkit/loopback` on `127.0.0.1`, not against Outline MobileProxy or another host proxy, and with synthetic runners: no production TCP-01, TLS-01, HTTP-01, DNS or NET-05 runner or proxy rule exists (DEV-454). No native binding passes a proxy (DEV-455). A proxied outcome is not evidence that the direct path is censored ([REQ-PROXY-0039](https://github.com/tv-rain/barometer-spec/blob/5d01879cfd1d47396c780befa2567f7e90439948/library/proxy.md#REQ-PROXY-0039)).

## Egress Network Context

When the host configures `network_context` at `Initialize`, each attempt acquires egress context through its own path snapshot. Public baseline: Draft `0.1.0` at [`32062c4`](https://github.com/tv-rain/barometer-spec/tree/32062c4bafcc29f5050ca6b78423f2acaefdde56) for [Network Context](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/network-context.md), the [Egress Object](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/data-formats/network-context.md#egress-object), [Proxy Network Context](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/proxy.md#network-context) and [Network Context Requirements](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/data-formats/task-execution.md#network-context-requirements).

- **Configuration.** `config.Decoder` validates the endpoints against the reviewed endpoint approvals ([Configuration Models](configuration-models.md)). Each initialized generation builds one `networkcontext.Lookup` from them, the reviewed classification approvals (classification versions, country and region codes) and the context trust roots, all trusted adapter inputs with no wire field. Without `network_context` there is no lookup: egress is `unavailable` and no endpoint is contacted ([REQ-CONTEXT-0008](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/network-context.md#REQ-CONTEXT-0008)). The endpoints cannot change for an initialized client; no task, `SetProxy` or other call reaches them.
- **Order.** After the capture, the access conditions and the network-change watch, the engine calls `Snapshot.Acquire` with a fetch bound to a fresh dialer of the attempt's path. Acquisition uses, in order, a fresh cache entry, one request to the primary and one request to the fallback through the same dialer; otherwise egress is `unavailable` ([REQ-CONTEXT-0020](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/network-context.md#REQ-CONTEXT-0020)). No endpoint is retried, no other path is used, and a valid primary response without classifications is successful and does not trigger the fallback. A response whose values the classification approvals do not permit is invalid, so the fallback is tried and nothing unapproved reaches a result. Results record `fresh` with `primary` or `fallback`, `cached` with `cache`, or `unavailable` with `none`, never the endpoint.
- **Request.** `execution.ContextFetch` makes one HTTPS `GET` with HTTP/1.1, TLS 1.2 or later and the configured trust roots (the system roots in production). The request carries the request line, `Host` and `Accept: application/json` only: no `User-Agent`, `Accept-Encoding`, cookie, authorization, identifier, address, target, task detail or `connection_code` ([REQ-CONTEXT-0012](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/network-context.md#REQ-CONTEXT-0012)). Redirects are not followed, connections are not reused and no environment proxy setting is consulted. Only a `200` response with an uncompressed `application/json` body of at most 4,096 bytes is valid; the body is decoded strictly, so unknown, duplicate or forbidden fields are invalid.
- **Bounds.** Each primary or fallback operation is bounded to 5,000 ms on the engine clock, and acquisition ends with the attempt deadline, a host cancellation, a proxy reconfiguration or a network change ([REQ-CONTEXT-0025](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/network-context.md#REQ-CONTEXT-0025)); the attempt then records that reason as `not_run`. The status line and headers are bounded to 8,192 bytes, a reviewed implementation input. The lookup dialer is not the metered attempt scope, so lookup bytes and connections do not count toward the attempt budgets and do not start the test.
- **Path.** A direct attempt's lookup uses the direct dialer. A proxy attempt's lookup uses CONNECT on the attempt's own proxy generation, which carries the endpoint name to the proxy, so no direct resolution or request occurs; a primary failure leads to the fallback through the same proxy, never to the direct path ([REQ-PROXY-0023](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/proxy.md#REQ-PROXY-0023)).
- **Cache.** `networkcontext.Cache` is one in-memory cache per client, never persisted. Its key is the access-network generation, the path name and the proxy generation, with no address or identifier ([REQ-CONTEXT-0024](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/network-context.md#REQ-CONTEXT-0024)). An entry is reused up to the registered default freshness of 300 seconds inclusive; the freshness is not configurable in this build. Storing an entry of a newer access-network generation drops the older generation's entries, `SetProxy` and `ClearProxy` drop every proxy entry ([REQ-PROXY-0016](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/proxy.md#REQ-PROXY-0016)), and failures are never cached. Each generation's lookup is bound to a cache epoch: building a generation for `Initialize` or a policy replacement starts a new epoch, and `Close`, clearing and the end of a generation drop its entries, so no generation reads or writes another's. `ClearMeasurementData` also erases the cache through the clearing registration point.
- **Requirements.** `execution.ContextConditions` evaluates `required_fields` and `allowed_country_codes` against the attempt's egress ([REQ-EXECUTION-0023](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/data-formats/task-execution.md#REQ-EXECUTION-0023)). A required field that is missing, including every field of an unavailable context, and an allowlist with an unknown country are `network_context_unavailable`; a known country outside the allowlist is `constraints_unsatisfied`. Before the first attempt either records `not_run` without running the test. Before a retry, `constraints_unsatisfied` ends the run without a result, as an access condition does, and `network_context_unavailable` is recorded and is a retry candidate when `retry_on` lists it. Without requirements an unavailable context does not block the attempt ([REQ-EXECUTION-0024](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/data-formats/task-execution.md#REQ-EXECUTION-0024)). `StartRun` does not acquire egress, so these requirements never produce `run_not_due`.

Limits: no real endpoint is chosen, deployed or contacted. Tests use synthetic HTTPS endpoints on `127.0.0.1` with a synthetic CA (`internal/testkit/contextendpoint`), reached through a name-mapping test dialer on the direct path and the scripted loopback proxy on the proxy path. Using real endpoints requires privacy-reviewed endpoints ([REQ-CONTEXT-0032](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/network-context.md#REQ-CONTEXT-0032)) and privacy and safety review before any field use; the endpoint observes the device's or proxy's public address and request time. Egress classifications are IP classifications, not physical location, and an endpoint failure or a classification is not evidence of censorship ([REQ-CONTEXT-0042](https://github.com/tv-rain/barometer-spec/blob/32062c4bafcc29f5050ca6b78423f2acaefdde56/library/network-context.md#REQ-CONTEXT-0042)). Native trust-root and network wiring belongs to DEV-455. Stricter local-policy context eligibility is not provided.

## Execution-Time Target Validation

The execution gate adopts public Draft `0.1.0` at [`bb805f07a36630db7250d5ab63006ed5e351f7a7`](https://github.com/tv-rain/barometer-spec/tree/bb805f07a36630db7250d5ab63006ed5e351f7a7), after internal alignment at `fc5fdf8733ad990f8363dcf4748edafa40b08dde` and the owner's confirmation that the scoped review is done ([GO-SPEC-ISSUE-015](specification-issues.md#go-spec-issue-015-resolved-address-validation-behind-a-hostname-connect-proxy)).

`Admitted.Targets` supplies owned copies of matched registrations and issuer/local-policy-authorized reachable redirect registrations. Their risk contributes to the admission intersection. `StartRun` constructs `execution.Targets` for that task/test, its selected path, trusted clock and local address policy, and places it on `Plan`. The attempt scope uses it before every network dial; a missing gate grants no destination. No runner receives the raw path dialer.

- **Initial contact.** The gate matches an exact authority, port and transport against current initial registrations, checks test/version, registration expiry and path, and applies the local address policy before contact. It does not treat query names or TLS SNI as connection authority.
- **Direct resolution.** An authorized hostname is resolved once under attempt cancellation. The complete returned set must be nonempty, at most 64 addresses and permitted by local address policy; an unsafe mixed set is refused atomically. The transport receives one checked literal IP, preventing a second DNS lookup or rebinding between check and dial. Expiry is checked again after resolution. Selection is bounded to the first checked address, with no hidden fallback or connection retry; a production runner must account for its registered address-family/protocol procedure. Resolver traffic uses the existing platform-resolver accounting exclusion, not an extra probe.
- **Proxy refusal.** Hostname authorities yield `proxy_path_unsupported` before resolution or proxy contact, including a late runner dial that preflight missed. The raw proxy dialer independently refuses them, so context or another internal call cannot send hostname CONNECT. A runner cannot hide a shared-gate refusal by returning a completed observation. Initial local-policy refusals use `local_policy_rejected`, not a TCP/TLS failure.
- **Redirects.** `Input.Redirect` checks a complete normalized tuple against an authorized parent link and returns a `measurement.TargetDialer` narrowed to that target. Its `Redirect` method narrows the next hop from that parent. Every child shares the original scope's byte/connection budgets, cancellation and cleanup; it cannot dial the initial target or another registered redirect instead. Hostname redirects on the proxy path, unregistered URLs on the same authority and prohibited destinations return the fixed `measurement.ErrTargetRejected` for a runner to produce its registered `redirect_rejected` outcome. These tests use synthetic runners; HTTP-01 parsing and its production runner remain pending.
- **Start and bounds.** A connection slot is reserved before resolver traffic. A local refusal refunds that slot and does not itself start the test. Direct resolver activity or a permitted transport operation starts it; an earlier test-owned network-state observation may already have done so. Refusal is `not_run` before test start and `incomplete` afterwards under REQ-RESULT-0051. A zero connection budget makes no resolver or transport call.
- **Address policy.** The default `task.PublicAddress` rejects local/private, documentation, benchmarking and other special-purpose destinations, including mapped private IPv4 and IPv6 special-purpose ranges, following the [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/) and [IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry/) tables inspected October 26, 2026. The static classification needs review when those registries change; it is not target approval or proof of routability. The unexported test adapter can supply a synthetic loopback-only policy; no public configuration or production native binding exposes that seam.
- **Context endpoints.** Proxy lookup skips hostname and prohibited-IP primary/fallback endpoints before calling a transport. One eligible fallback may be tried on the same proxy generation. Required unavailable context prevents the test from starting; optional unavailable context may accompany an otherwise eligible measurement. Direct context resolves and checks addresses before a pinned-IP connection while preserving the configured URL and TLS hostname. Cache entries are process-local and can only be populated by the current eligibility path; reinitialization/policy/proxy changes invalidate their existing keys/epochs.

The shared-gate tests are synthetic Go evidence only. Native integration, production HTTP/NET-05 codecs and runner usage of the redirect capability, independent interpretation review, field validation and release support remain separate work. No per-task manifest rebaseline is performed.

## Runtime Case Families

DEV-640 classifies the 49 runtime-scope cross-cutting families for the runtime and execution closeout (DEV-576): the `CC-EXECUTION-*`, `CC-SCHEDULE-*` and `CC-LIMIT-*` families, their `RV-` review cases, and the run-dependent `CC-RESULT-EXECUTION-OBJECT`, `CC-RESULT-TIME-OBJECT`, `CC-SAFETY-USER-CONSENT`, `CC-OPTIONS-EXECUTION-PRECEDENCE`, `CC-CONTEXT-FORMAT-USE-IN-EXECUTION`, `CC-CONTEXT-EXECUTION-INTEGRATION`, `CC-PROXY-EXECUTION-STATES` and `CC-TRUST-LOCAL-POLICY-LIFECYCLE-RUNTIME`. A family is executed only when every row of its case plan runs with synthetic adapters, the injected clock and the test-only loopback runner. Mixed families are not split, and planned cases are not conformance.

Where a plan names a registered test only as the vehicle for a schedule or execution rule (for example the NET-01 tasks of `CC-SCHEDULE-SCHEDULING-MODEL-TIME-WINDOW`), the synthetic runner registered under the TCP-01 identifier stands in for it, and no behavior of the named test is asserted. This substitution was approved for DEV-640.
