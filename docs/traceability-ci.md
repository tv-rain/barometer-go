# Traceability CI Checks

DEV-475 adds the `Traceability and conformance smoke` job to the existing CI workflow. It checks working-tree manifests and requirement-reference comments, runs the public checker's synthetic positive/negative suite and the Go conformance fixture smoke tests, and retains full JSON metadata reports as a CI artifact for 14 days. Compilation and synthetic cases establish no runtime, platform or field support.

## Reproduce Locally

Use Go 1.26.0 or later, Git, tar, and Python 3.10 or later with the public tooling's pinned packages. CI uses Python 3.14. Supply an explicit public specification checkout with full history containing commits `d93aff93cbc17e7c065fb40d8f6e2e01a697bf35`, `5a37e82865a08922c4821c7318656286933421e5` and `a944ed6c389fec9f0d089f0044ead6fe845328b1`; no private repository is required. The script never fetches, installs packages or discovers sibling checkouts. Dependency installation is a separate network operation.

From this repository, with the public checkout at the explicitly selected example location:

```sh
python3 -m venv /tmp/barometer-traceability-venv
git -C ../barometer-spec show d93aff93cbc17e7c065fb40d8f6e2e01a697bf35:scripts/requirements.txt > /tmp/barometer-traceability-requirements.txt
/tmp/barometer-traceability-venv/bin/python -m pip install -r /tmp/barometer-traceability-requirements.txt
make traceability PYTHON=/tmp/barometer-traceability-venv/bin/python SPEC_CHECKOUT=../barometer-spec REPORT_DIR=/tmp/barometer-traceability-reports
make check
```

The pinned dependency file is the public tooling's `scripts/requirements.txt` at the tooling commit above; CI installs the same file. Use a Go 1.26 toolchain first on `PATH`; the public checker tests build their helper with `GOTOOLCHAIN=local`, so an older default `go` that would otherwise switch toolchains fails. If `go version` outside this module reports an older release, prepend a Go 1.26.0+ `bin` directory to `PATH` for the command, for example `PATH="$(go env GOROOT)/bin:$PATH"` run from inside this module where automatic selection has already chosen Go 1.26. Before any checkout export or test, the driver checks that the `go` first on `PATH` (with `GOTOOLCHAIN=local`) meets the `go.mod` directive, that the selected Python is 3.10 or later, and that it can import `jsonschema`. It reports every missing prerequisite and exits with status 2; `scripts/test_traceability_ci.py` covers these failure paths. Both checkouts need the selected immutable commits, including Go inventory commit `c06ce6b7b73b8520f35ce10982315fcb4d05615b` and the manifests' implementation baselines. Reports must be outside both checkouts. The driver exports the public tooling/source snapshot from its pinned Git commit into temporary storage, builds the standard-library declaration helper there, and removes that storage on exit. Working-tree changes to the supplied public checkout cannot select executable tooling or schema. Python packages are development dependencies, with no Go module dependency or change to `make check` prerequisites.

## Checks and Failure Rules

- Validate public catalog integrity and Go working-tree `.md`/`.go` requirement-reference comments against the pinned public source snapshot.
- Require every Go working-tree `// requirement-ref` ID to be active in the pinned public catalog, mapped in a current manifest, and linked to the citing file: a source file must be an implementation location of that ID and a `_test.go` file must be the location of a case mapped to it (DEV-569). `requirement-history` citations and Markdown plans are excluded. Links are metadata; they do not establish implementation or a passing case.
- Run the public tooling tests, including broken references, false implementation/support claims, stale baselines, malformed metadata and the public invalid scenarios, using synthetic local Git repositories.
- Validate each working-tree manifest with the canonical public checker and independently selected specification/implementation commits. Existing paths, selectors, issue/evidence references and support gates are checked against those immutable objects.
- Compare each manifest's allocated IDs with its original mapping at the independent Go inventory commit. Removal of an allocated ID or its target/case mapping fails, even though partial-mode metadata alone permits omissions. The only exception is an ID that the public catalog marks retired at the manifest's pinned specification baseline. It may leave the current manifest only when every declared successor keeps a target and case mapping.
- Reject vague case plans in the current manifests (DEV-572): an automated plan led, in any sentence or coordinated clause, by Review, Inspect or Plan; an automated plan shorter than 100 characters after its family-class prefix; plan text shared by two cases; a plan naming a requirement ID it is not mapped to; and an `RV-` review case without its fixed opening, reviewer role, reviewed artifact, checklist, evidence record and own Markdown heading. `UT.*` cases are exempt from the wording rules. The driver prints automated, review and unit-test case counts separately; review cases are not automated coverage. See [typed review cases](traceability-manifest.md#typed-review-cases).
- Require each registered historical manifest under `traceability/historical/` to be byte-identical to its original at the recorded source commit (the inventory commit, `c5f4e92e06936cb677c7a03e9769ff75b1f51874` for the DEV-568 cross-cutting and DEV-473 measurement manifests, `60d64a606bdd19fa5d326c68a6157e7760b28ff1` for the DEV-569 manifests, `c2b269042eaa5dff85027b46ccbea4dec9eb73a0` for the DEV-572 cross-cutting manifest, `a3e167c91c112e2da8b809be26fd76440cc74c95` for the DEV-582 cross-cutting manifest, `6aa8a744351b6faf3020de5433041f16e0b411f1` for the DEV-583 cross-cutting manifest, `112812735d3b6c20a5afd2276e5320ef31432114` for the DEV-597 cross-cutting manifest, `e039022bd8318831bb628152d31e6a5b02a1b1f2` for the DEV-586 cross-cutting manifest, `922d2457453a55e6b45cc0627dd8939047e97d69` for the DEV-587 cross-cutting manifest, `2c933f6db830533fa4fba1aff0463cbc6041c765` for the DEV-588 cross-cutting manifest, `e039c6acdcaa71d319eecb29a32d0513efb76324` for the DEV-589 cross-cutting manifest, `1aacc2de366689cf05e39cdda6289f723c363ce1` for the DEV-590 cross-cutting manifest, `ef968d6963006f1b0db109059deb703bc9c6c366` for the DEV-591 cross-cutting manifest, or `b5e9a332b1d3ef05c130f7413d66e817ad2dd825` for the DEV-600 cross-cutting manifest, `f4acea7323a38b112bfbc69e2bc49f391079e6b1` for the DEV-592 cross-cutting manifest, `484d72e0837528a53237bbd6b46bd6ab5b883828` for the DEV-593 cross-cutting manifest), and validate it at its original baselines. Missing or unregistered top-level manifest files fail. New allocations and baseline changes require deliberate review of the driver's inventory and baseline policy.
- Run `go test -count=1 ./internal/testkit/conformance` against the current checkout. The ordinary Go CI job continues to run `make check` independently.

The driver exits nonzero for any failing command, invalid manifest, inventory loss or setup error. It writes complete checker reports, including every permitted gap and review assertion, and prints finding counts plus individual errors. CI uploads reports even when validation fails. No report is substituted for execution of a mapped case.

The driver labels all of these checks historical, including the current mapping, because it validates committed metadata against declared objects rather than a moving branch. They validate preserved metadata against its declared objects; they do not promote old evidence into current implementation claims or combine differently based manifests into a single conformance report.

Planned targets/cases and declared unallocated sources remain permitted, visible gaps. A `partial` requirement with a passing `UT.*` case keeps its missing-conformance gap while any mapped planned family is unexecuted. The CI job does not re-execute the evidence cases at their baseline; the ordinary CI job runs the current tests. The inventory gate prevents loss of previously allocated mappings; it does not infer untagged obligations or require unfinished implementation to pass. Changes to case meaning, semantic completeness, inventory completeness, evidence authenticity and issue closure/adoption still require human review. Adding an ID or preserving a nonempty case list cannot prove coverage. Future source allocations require reviewed pin/inventory updates; this job does not track a moving public branch.

Keep historical committed reports unchanged. New CI outputs include a provenance record with tooling, inventory and consumer revisions. During local development, the consumer revision names HEAD while manifests, reference comments and synthetic tests include uncommitted changes; such a run is local validation, not immutable committed evidence. No measurement, public API, native adapter, release or support status is changed by this task.
