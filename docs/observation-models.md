## Decoding and Encoding

Observation and context formats have no independent wire version field. `DecodeProtocol` and `NewContextDecoder` require the caller to select the enclosing `0.1.0` contract explicitly; other versions fail without fallback. Their callers must separately validate the enclosing result and registered test/result versions. No version property is added to serialized models.

Both decoders use `internal/jsondecode` before constructing a model. Unknown fields, duplicate decoded member names, invalid Unicode, nulls, wrong types, non-canonical integer tokens and missing required fields fail atomically. Errors contain fixed classes without payloads. Zero models cannot serialize. Direct JSON import into a model is rejected, including replacement of an existing model; callers must retain the newly returned value after successful explicit decoding. Serialization reconstructs closed wire objects rather than retaining input bytes. Optional fields remain absent, permitted `unknown` values remain explicit, and required zero/false fields remain present.

Protocol input is limited to 65,536 encoded bytes, depth 8 and 256 value nodes. The operation duration has an implementation-local maximum of 60,000 ms and must be a nonnegative multiple of 250 ms. Registered runners still own their stricter operation deadlines, execution order, stage emission, allowed types and terminal-result constraints. A failed observation needs a registered failure of its type; succeeded/incomplete observations have no failure. The accepted REQ-OBS-0051 contract explicitly forbids failure fields on incomplete observations of all four types.

HTTP decoding takes `ProtocolLimits` from the validated enclosing test: configured body bound, redirect count and status/header/body check presence/counts. These inputs contain no target or check values. They cannot exceed registered maxima of 65,536 body bytes, two redirects, eight header checks and eight body checks. The model checks status ranges, check kinds/indexes/duplicates, required nested fields, body/redirect bounds and failure evidence. Check outcomes expose only kind/index/matched. Full configured-check completeness, test outcomes, per-response sequencing and test-specific constraints remain the runner/result owner's responsibility. No headers, body bytes, digest, redirect URL or destination field exists in the model schema.

`DNSDetails`, `DNSResponse`, `DNSAnswer`, `TCPDetails`, `TLSDetails`, `HTTPDetails`, `Redirect`, `Body`, `Check`, `Access` and `Egress` are detached view records, not independently validated models. Their JSON serialization is explicitly blocked; only the validated containing `Observation`, `AccessSnapshot` or `NetworkContext` can produce wire objects. Returned nested pointers/slices are copied; modifying a view cannot change the model.

## DNS and TLS Models

DNS models enforce the 16,384-byte encoded observation bound (including original whitespace), three-response/16-answer/eight-CNAME bounds, required arrays, sequential arrival indexes, nondecreasing quantized offsets within the observation duration, registered engines, query types and response codes. Non-UDP observations retain at most one response. `ProtocolLimits.MaxDNSResponses` may select a stricter UDP response count; zero selects the registered structural ceiling of three. A response-limit marker must be true and correspond to the effective UDP count. This model does not prove that a collection window was active or select a multi-response test outcome; the runner retains conflict/count-limit precedence.

Exact DNS answers require the separate trusted `RetainDNSAnswers` input, which the future owner may assert only for a reviewed non-sensitive query. Absence of that input forbids nonempty answers. It is a structural gate, not proof that target/privacy review happened. Answers contain only the requested A/AAAA family or intervening CNAME values. IPs must be canonical, nonmapped, zone-free public values under the conservative fixed retention filter below. CNAME values must already be normalized lowercase ASCII DNS labels within 63-byte label/253-byte name bounds; the protocol owner performs IDNA normalization before this leaf model. The model does not perform IDNA conversion, DNS lookup, enrichment or a new connection to an answer.

The fixed IP filter rejects non-global/private/mapped/scoped values, selected special-purpose IPv4 ranges and conservative IPv6 aggregates; IPv6 retention is restricted to `2000::/3`, excluding the aggregates listed in `dns.go`. Its selection was checked against the [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/iana-ipv4-special-registry.xhtml) and [IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry/iana-ipv6-special-registry.xhtml) special-purpose tables on October 15, 2026. Aggregate exclusions intentionally reject some more-specific globally reachable exceptions. This is a stricter local retention policy, not a live registry, comprehensive allocation oracle or reachability test. A response outside this filter fails model construction atomically; it is never partially appended, replaced or silently clamped. Broader address retention requires explicit review.

Serialized DNS answers must already be deduplicated. `NewDNS` is the producer constructor: it consumes bounded normalized answers, removes exact duplicates in first-occurrence order, builds the closed wire representation and applies the same validation. It rejects more than 16 input entries before deduplication or allocation and never truncates distinct data. Required empty response/answer arrays serialize as arrays. Getters deep-copy responses and answers. A single complete response with a nonzero code requires the corresponding registered failure; multi-response and incomplete-output precedence remains the enclosing runner/result owner's responsibility.

TLS models use the accepted closed version, negotiated-ALPN, certificate-validation and coarse peer-alert classes. Succeeded TLS observations require trusted local certificate validation. Certificate failure labels must agree with their local validation class. An alert detail is legal only on a failed/alert observation; a peer certificate alert does not rewrite local certificate validation. Optional absent fields remain absent. `NewTLS` provides the bounded producer constructor using the same validator; direct JSON encoding of detached TLS views is blocked.

`DNSResponseCode`, `NegotiatedTLSVersion`, `NegotiatedALPN` and `PeerAlertClass` are pure `0.1.0` mappings of safely observed, typed facts. Their exposed flag distinguishes unavailable data from an observed value outside the retained subset. They do not parse packets, errors or TLS records, establish peer reception, infer negotiation, choose a failure/outcome or authorize a network operation. The future reviewed protocol/API adapter must supply the complete effective DNS code and genuinely negotiated values, not legacy record headers. Unexposed values yield no field/response evidence; unlisted observed values use only the explicitly registered coarse marker. `ValidateALPNOffer` checks the three offered identifiers, duplicates, count and exact selected contract for future registered-test validators; it does not implement task admission or create an offer. Serialized decoding rejects unregistered strings without calling these producer mappings to repair them.

## Context Binding and Reviewed Categories

`DecodeAccess` supports the access-only NET-01 representation before egress path selection, under a stricter local 1,024-byte, depth-2, 16-node bound. It returns an immutable `AccessSnapshot` with a separate positive access generation. `MatchesGeneration` refuses another generation or a snapshot marked changed; only the coarse access fields serialize. A Network Context can project its already validated access snapshot without egress metadata. This is not a NET-01 runner or platform collector.

`NewPath` accepts one positive access-network generation, a direct/proxy path and, for proxy only, a positive proxy generation and bounded connection category. Direct paths reject proxy metadata. A path rejects JSON import/export. `ContextDecoder.Decode` requires that local path separately and validates exact agreement with the serialized egress path/category. Endpoint data cannot supply generations.

`NetworkContext.Matches` checks the complete local binding and refuses a snapshot marked `network_changed`. Different access generations, paths, proxy generations or connection categories cannot match. Capturing authoritative generations, initialization isolation, freshness/expiry, detecting network changes, cache invalidation and stopping attempts are future runtime responsibilities. This pure value does not monitor a network or implement cache behavior.

Context input has a stricter implementation-local 4,096-byte bound, depth 5 and 64 value nodes. Serialized context never includes the local binding. Fresh context requires primary/fallback source; cached requires cache source; unavailable requires none and forbids classification fields. Missing optional country, region and ASN remain unknown, including a fresh response with no classification. Invalid data never becomes unavailable or another path implicitly.

`ContextApprovals` are trusted integration inputs separate from context JSON, analogous to the existing initialization approval boundary. They explicitly list reviewed non-user-specific proxy categories and classification versions and reviewed ISO 3166-1 country/ISO 3166-2 region assignments. Each list has a local maximum of 256 unique values. Versions use a stricter local 1–64 printable ASCII-byte bound. Countries/regions are normalized to uppercase and checked against approved assignments; region syntax and the matching country prefix are additionally checked. The integration owner must verify actual ISO assignment and the necessity/reliability of region retention before approval; this model neither embeds an ISO dataset nor verifies an approval's authority. Syntax alone must never be treated as evidence of ISO assignment. Approval lists are copied and cannot be expanded by endpoint data. Unknown optional classification does not require any country or region approval.
